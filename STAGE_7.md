# Этап 7: отчёты за период, миграции и копии базы

Обновление ставится поверх этапа 6. Оно не содержит вашу базу, пароли и
резервные копии. Python-код вручную вставлять в редактор не нужно.

## 1. Подготовка

1. Остановите сервер клавишами Ctrl+C. Скопируйте `backend/inventory.db`
   в отдельную папку вне проекта. Не удаляйте исходный файл.
2. Откройте корень репозитория в VS Code. Выполните `git status`.
   Если есть незакоммиченные изменения или незавершённое слияние, сначала
   сохраните предыдущий этап и разберите состояние Git.
3. Убедитесь, что этап 6 объединён с main. При чистой папке:

```powershell
git switch main
git pull --ff-only origin main
git switch -c stage-7-reports
```

При ошибке остановитесь на ней. Не используйте `--force` или
`reset --hard`. Если файлы этапа 7 уже перенесены, не делайте pull
поверх них: сначала проверьте `git status`.

## 2. Перенос обновления

Распакуйте архив и перенесите его содержимое в корень, объединяя папки
и заменяя только одноимённые файлы. Не заменяйте frontend и backend целиком.
Сохраняйте `.git`, `.env` и `backend/inventory.db`.

Обновятся:

- `backend/migrations/`: зафиксированная схема этапа 6 и первая миграция;
- `backend/app/schema.py`, `db_tools.py`: контроль версий и команды копирования;
- `backend/app/routers/reports.py`: серверный расчёт и экспорт Excel;
- `backend/app/main.py`, `database.py`, `manage_users.py`: запуск с миграциями;
- `backend/requirements.txt`, `backend/Dockerfile`, `.dockerignore`,
  `.gitignore`, тесты и инструкции;
- `frontend/index.html`, `frontend/js/app.js`,
  `frontend/js/period-report.js`: выбор периода и выгрузка.

## 3. Обновление базы и запуск

В терминале из корня:

```powershell
cd .\backend
py -m pip install -r requirements.txt
py -m app.db_tools upgrade
py -m app.db_tools status
```

Первая команда upgrade для существующей SQLite создаёт проверенную копию
в backend/backups, сверяет таблицы со схемой этапа 6 и регистрирует версию.
Если структура отличается, автоматический переход останавливается;
не удаляйте базу, пришлите текст ошибки. Полное резервирование через эту
команду поддерживается для файловой SQLite, а не для PostgreSQL.

Должна появиться версия `0001_stage6`. Это нормально: она фиксирует
структуру базы, которая сформировалась к шестому этапу. Данные не
очищаются, администратор остаётся прежним.

Запустите сайт:

```powershell
py -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Откройте http://127.0.0.1:8000/, при необходимости обновите Ctrl+F5.
Войдите старым логином и паролем. Если база новая и пустая, после
upgrade создайте администратора по инструкции STAGE_6.md.

По умолчанию приложение всегда ищет `backend/inventory.db`, независимо
от рабочей папки. Если задан DATABASE_URL, он имеет приоритет.

## 4. Выгрузка за месяц / квартал / год

1. Откройте «Отчёты → План списания за период».
2. Выберите год, тип периода и номер месяца либо квартала.
3. Выберите режим и нажмите «Сформировать».
4. Проверьте список и нажмите «Скачать Excel».

В Excel два листа: «Кандидаты на списание» и «Параметры».
На первом: инвентарный номер, название, категория, локация,
ответственный, дата покупки, стоимость, остаток, амортизация,
текущий статус и причина. На втором: границы периода, правила расчёта
и итоги. Отчёт доступен обеим ролям, менять правила может администратор.

### Как понимается период

«Все кандидаты на конец периода» включает достигших порога к концу
периода и технику, которая сейчас отмечена как потерянная.
Для амортизации отдельно видно, достигнут порог раньше или в этом периоде.

«Впервые достигших порога в периоде» сравнивает амортизацию накануне
начала периода и в последний день периода. Потерянная техника включается
сюда только при достижении порога амортизации: отдельной даты потери в
проекте пока нет.

Пример для защиты: цена 10 000, дата покупки 2025-04-01,
индивидуальный срок 10 месяцев, минимум 0%, порог 90%.
В январе 2026 проходит 9 календарных месяцев: амортизация 90%,
остаток 1 000. Устройство войдёт в «новые» за январь,
I квартал и 2026 год. За февраль в «новые» уже не войдёт,
но останется в «все кандидаты». Настройки задайте в
«Отчёты → Правила амортизации», а пример техники создайте в реестре.

Расчёт использует текущие стоимость, статус и правила; это не восстановление
состояния базы на прошлую дату и не бухгалтерский акт списания.
Уже списанная техника исключается. Без даты покупки/ненулевой цены
амортизация не начисляется. Изменения базы между просмотром и скачиванием
попадут в выгрузку: файл заново считается на сервере на момент скачивания.
Ни одна кнопка отчёта автоматически не списывает устройства.

## 5. Создать и проверить копию

В другом терминале из backend:

```powershell
py -m app.db_tools backup --output .\backups\demo-stage7.db
py -m app.db_tools verify .\backups\demo-stage7.db
```

Если такое имя уже существует, выберите новое. Команда не перезаписывает
старые копии. Без --output создаётся имя с датой и временем:

```powershell
py -m app.db_tools backup
```

Используется SQLite Backup API, а не обычное копирование открытого файла;
проверяются целостность, связи, таблицы и количество основных записей.
Проверка показывает числа, а не логины, пароли или содержимое карточек.
Копия содержит всю базу, включая хеши паролей: храните её закрыто,
не прикрепляйте к публичному репозиторию. Для реальной защиты держите
отдельную копию на другом носителе: папка на том же диске не защищает
от поломки самого диска.

## 6. Проверить восстановление, не меняя рабочую базу

Остановите сервер Ctrl+C. Из backend выполните:

```powershell
py -m app.db_tools restore-copy .\backups\demo-stage7.db --output .\restore-test\inventory.db
py -m app.db_tools verify .\restore-test\inventory.db
```

Команда создаёт отдельный файл. Если он уже существует, выберите новое
имя. Рабочую inventory.db она не заменяет. Старые сеансы входа удаляются
только из восстановленной копии; пароли, карточки и история сохраняются.

Чтобы посмотреть восстановленную базу в браузере, в том же терминале:

```powershell
$env:DATABASE_URL = "sqlite:///./restore-test/inventory.db"
py -m uvicorn app.main:app --host 127.0.0.1 --port 8001
```

Откройте http://127.0.0.1:8001/ и войдите логином из копии.
Сверьте устройства, ремонты и сохранённые проверки.
После демонстрации нажмите Ctrl+C, затем:

```powershell
Remove-Item Env:DATABASE_URL
py -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Теперь снова работает исходная база. Для старой копии без версии
нужно сначала выполнить upgrade именно для её DATABASE_URL.
Не заменяйте рабочую базу без остановки сервера и отдельной копии её
текущего состояния. Восстановление старого снимка не возвращает изменения,
сделанные после его создания.

## 7. Отправить код на GitHub

Во втором терминале из корня проекта:

```powershell
git add -- .gitignore .dockerignore README.md STAGE_7.md backend/requirements.txt backend/Dockerfile ':(glob)backend/**/*.py' frontend/index.html frontend/js/app.js frontend/js/period-report.js
git diff --cached --name-only
```

В списке должны быть только код и инструкции. Не загружайте файлы базы,
backups, restore-test, реальные отчёты, .env и ZIP. После проверки:

```powershell
git commit -m "Этап 7: отчёты за период, миграции и копии базы"
git push -u origin stage-7-reports
```

На GitHub: Compare & pull request → base main, compare stage-7-reports →
Create pull request → проверка файлов → Merge pull request.
При конфликте остановитесь и разберите его; не делайте push --force.

## Технические границы

Миграция фиксирована в backend/migrations/versions: изменение моделей
само по себе больше не меняет базу. Сервер откажется запускаться,
если миграция ещё не применена. Следующие изменения схемы нужно оформлять
новыми версиями миграций, а не редактировать старую.

Команды backup/verify/restore-copy предназначены для SQLite.
Для PostgreSQL сначала отдельно сделайте pg_dump и проверьте восстановление.
Для новой PostgreSQL-базы можно выполнить upgrade в контейнере;
для существующей потребуется --backup-confirmed, который сам копию
не создаёт. В Docker миграции запускаются отдельной командой:
docker compose run --rm backend python -m app.db_tools upgrade.
На SQLite этот этап проверен автоматически; PostgreSQL и Docker здесь
не запускались. Публичный HTTPS-хостинг остаётся следующим этапом.
