# Этап 6. Вход и права доступа

Это обновление поверх этапа 5. Оно не содержит базу данных и пароли.
Готовую рабочую папку не удаляйте. Настройка хостинга в этот этап не входит.

## 1. До переноса файлов

1. Остановите сервер клавишами Ctrl+C. Сделайте копию файла
   `backend/inventory.db` в отдельную папку вне репозитория.
2. Откройте корень репозитория в VS Code. Здесь должны быть `frontend`,
   `backend`, `README.md` и скрытая папка `.git`.
3. В терминале выполните `git status`. Если есть конфликты, незавершённое
   слияние или незакоммиченные изменения, сначала разберите их. Не используйте
   `reset --hard`, `push --force` и массовый выбор своей версии файлов.
4. Если этап 5 отправлен в отдельную ветку, убедитесь, что его pull request
   объединён с main. При чистой рабочей папке выполняйте команды по очереди:

```powershell
git switch main
git pull --ff-only origin main
git switch -c stage-6-auth
```

Если какая-то команда завершилась ошибкой, не выполняйте следующую:
пришлите текст ошибки и результат `git status`.

## 2. Что перенести из архива

Перенесите содержимое распакованного архива в корень репозитория,
объединяя папки и заменяя одноимённые файлы. Не заменяйте папки целиком.
Вручную вставлять Python или JavaScript в редактор не нужно.

| Файлы | Изменение |
| --- | --- |
| `backend/app/security.py` | Проверка сеансов, CSRF и прав доступа |
| `backend/app/routers/auth.py` | Вход, выход, пользователи и блокировка |
| `backend/app/manage_users.py` | Создание первого администратора и сброс пароля |
| `backend/app/main.py`, `models.py`, `backend/requirements.txt` | Защита API, новые таблицы и библиотека хеширования |
| `frontend/js/auth.js` | Форма входа, роли и управление пользователями |
| `frontend/js/app.js`, `inventory-api.js`, `frontend/index.html`, `styles.css` | Сеанс в интерфейсе и защита действий |
| `backend/tests/conftest.py`, `test_auth.py`, `test_api.py` | Проверки доступа и функций прошлых этапов |
| `docker-compose.yml`, `README.md`, `STAGE_6.md` | Настройка контейнера и инструкции |

Не удаляйте `.git`, `.env`, `backend/inventory.db`, остальные файлы
`frontend` и `backend`. Пользователи, как и техника, хранятся в базе,
а не на GitHub.

## 3. Установить зависимости и создать администратора

В терминале из корня:

```powershell
cd .\backend
py -m pip install -r requirements.txt
py -m app.manage_users create --username admin --role admin
```

Придумайте собственный пароль длиной от 12 до 128 символов.
Введите его два раза. Символов при вводе не видно: так и должно быть.
Не вводите пароль в командной строке аргументом и не отправляйте его в чат.
Готового общего пароля в проекте нет.

При сообщении «Логин уже занят» используйте существующую запись или
сбросьте пароль локально:

```powershell
py -m app.manage_users reset-password --username admin
```

Сброс аннулирует активные сеансы этого пользователя. Базу удалять не нужно.

## 4. Запустить и войти

Из той же папки backend:

```powershell
py -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Дождитесь Uvicorn running и не закрывайте терминал.
Откройте http://127.0.0.1:8000/ в браузере. Если видна старая версия,
обновите страницу Ctrl+F5. Войдите под логином admin и своим паролем.
При следующем запуске создание администратора повторять не нужно.

Если виден только демонстрационный реестр без входа, вы открыли автономный
фронтенд. Перейдите на указанный адрес Python-сервера, а не в файл index.html.

## 5. Проверить роли

Войдите как администратор, откройте «Пользователи» и создайте сотрудника:
логин латиницей, пароль от 12 символов, роль «Сотрудник».
Для проверки откройте другое окно в приватном режиме и войдите им.

| Действие | Администратор | Сотрудник |
| --- | --- | --- |
| Читать реестр, паспорта, отчёты, историю и печатать метки | Да | Да |
| Сохранять инвентаризацию, открывать и закрывать ремонты | Да | Да |
| Добавлять, редактировать и списывать устройства | Да | Нет |
| Импортировать CSV/Excel, менять справочники и амортизацию | Да | Нет |
| Создавать пользователей и блокировать сотрудников | Да | Нет |

У сотрудника нет кнопок изменения реестра, импорта и пользователей.
Сервер также запрещает эти запросы, даже если отправить их вручную.
В этой версии администраторов нельзя блокировать из интерфейса.
Логины и роли существующих пользователей не редактируются.

Нажмите «Выйти»: сеанс удаляется из базы, а не только скрывается экран.
После блокировки сотрудник теряет доступ и не сможет войти снова,
пока администратор не разблокирует его. QR-ссылка открывает паспорт
только после входа, сохраняя выбранное устройство.

## 6. Отправить код в GitHub

Откройте второй терминал в корне репозитория. Если вы остались в backend,
сначала выполните `cd ..`. Проверьте `git status`: текущая ветка должна
быть stage-6-auth.

```powershell
git add -- README.md STAGE_6.md docker-compose.yml backend/requirements.txt ':(glob)backend/**/*.py' frontend/index.html frontend/styles.css ':(glob)frontend/js/*.js'
git diff --cached --name-only
```

Проверьте список: только код и инструкции. Там не должно быть `.env`,
`inventory.db`, паролей, архивов и реальных выгрузок Excel. Если они есть,
остановитесь; не публикуйте их. Убедитесь также, что `.gitignore`
содержит `.env`, `*.db`, `__pycache__/` и `.venv/`.

```powershell
git commit -m "Этап 6: вход и роли пользователей"
git push -u origin stage-6-auth
```

На GitHub нажмите Compare & pull request, выберите base: main
и compare: stage-6-auth, затем Create pull request.
Проверьте изменения и, если конфликтов нет, нажмите Merge pull request
и подтвердите. GitHub хранит код, но не запускает Python-сервер.
Учётные записи и локальная база автоматически туда не переносятся.

## 7. Что сказать и показать на защите

«Добавили аутентификацию по логину и паролю и авторизацию по ролям.
Первого администратора создаём локальной командой. Он выдаёт доступ
сотрудникам. Пароли хранятся в виде Argon2-хешей, а сеансы отзываются
при выходе и блокировке. Запреты проверяются на сервере, а не только
скрывают кнопки».

Покажите вход администратора, создание сотрудника, его ограниченный
интерфейс в другом браузере и отказ доступа после блокировки.

## Технические границы

- Сеанс живёт до 8 часов. Cookie HttpOnly, SameSite=Strict;
  значение сеанса хранится в базе как SHA-256-хеш. Пароли хешируются Argon2.
- Изменяющие запросы проверяются CSRF-токеном; токены не кладутся в
  localStorage. Десять неуспешных попыток с одного IP ограничивают вход
  до окончания пятиминутного окна. Кнопка выхода отзывает текущий сеанс.
- Общедоступной регистрации и восстановления через почту нет;
  забытый пароль сбрасывается командой из шага 3.
- Автономное демо осталось отдельно и не содержит данных серверной базы.
- Для HTTPS-хостинга задайте AUTH_COOKIE_SECURE=true и настройте
  постоянную БД, резервные копии, доверенный reverse proxy и
  ограничения нагрузки. В локальном HTTP-режиме эта переменная false.
  Не считайте один этот этап полной подготовкой к публичному хостингу.
